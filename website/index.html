A general-purpose harness you can trust more

OlivIA is built to be the reusable substrate under any agentic workload. You describe an agent and the services that invoke it in one TOML file; the harness exposes the matching endpoints and routes every request through the same sandboxed loop. Swap the prompt, the tools, and the data stores, and the same runtime becomes a support bot, an ETL scheduler, a research assistant, or an internal automation — with the identical safety guarantees.

That trust is structural, not hoped-for. OlivIA's architecture narrows what the model can do — and where unexpected behaviour can go — in three ways: it enforces the communication layer with strongly typed messages, so the model can only emit a validated envelope rather than free-form actions; it denies the model full control, keeping it a router that delegates instead of an operator that executes; and it sandboxes every tool inside a WebAssembly sandbox, so tool code runs with only the capabilities it was explicitly granted.

Two ideas, enforced

The model is a router, not a solver, and tools are untrusted code, so they run sandboxed. Everything else follows from these.

Bounded blast radius

The worst a jailbroken model can do is "call tool X"; the worst a buggy tool can do is limited to the handful of capabilities it declared.

Language-agnostic tools

A tool is any wasm32-wasip2 component implementing one WIT contract — write it in Rust, JS, Python, Go, or C.

One config, many surfaces

HTTP endpoints, a Telegram bot, and cron triggers all invoke the same agent — declared in a single file.

Architecture

A request enters, the agent routes, a tool runs sandboxed.

A trigger arrives through a service, is handled by the agent, and the agent runs an agentic loop: ask the model what to do, run the chosen tool in a fresh sandbox, feed the result back, repeat — until the model answers done or error.

The agentic loop

The model never does the work. Wrapped in a strict developer prompt (the tool catalogue, the data stores, the rules), it replies with a small JSON envelope — nothing else.

  1. 1
    Plan. The harness sends the running conversation to the model via LiteLLM.
  2. 2
    Act. The model returns {"state":"tool", …}; the harness runs it in a fresh sandbox.
  3. 3
    Observe. The tool's output is appended to the conversation and the loop repeats.
  4. ✓
    Finish. On done/error the agent replies to the caller. Bounded by MAX_ITERATIONS.
model → harness
{
  "state": "tool",
  "name": "web_search",
  "params": "{\"query\":\"…\"}"
}

// or, when finished
{ "state": "done", "result": "…" }

One contract: the WIT world

The host/guest boundary is described once as a WIT world. Both the harness and every tool generate bindings from it, so the ABI is checked at compile time. A tool exports two functions:

  • info() — its name, description, params schema, and the permissions it needs.
  • run(input) — receives JSON params, returns { state, content }.

Each call gets a fresh, sandboxed instance — tools accumulate no state between invocations.

tools/tool.wit
world tool-world {
  enum permission { network, file-system }

  record tool-info {
    name: string,
    description: string,
    schema: string,
    permissions: list<permission>
  }

  export info: func() -> tool-info;
  export run: func(input: string) -> tool-output;
}

Security model

Defense in depth for code you can't trust.

The threat model is blunt: an LLM can't be trusted to be correct, and it can't be trusted with arbitrary execution. OlivIA contains both with two independent layers — so even a fully jailbroken model driving a buggy tool is bounded to a small, enumerated capability set.

01

The model has no execution surface

The developer prompt makes it a strict router: zero internal logic, always delegate, emit only the JSON envelope. The one thing it can cause is "call tool X with params Y" — and the harness validates the tool name against the registry, so it can't invent a tool that isn't there.

02

Tools are sandboxed WebAssembly, deny-by-default

Every tool is a memory-isolated wasm32-wasip2 component run under a capability-based WASI sandbox that grants nothing by default. A tool holds only the capabilities it declared in info() — there is no path from a clever prompt to arbitrary code on the host.

The permission model

ToolState::new() reads a tool's declared permissions and hands its sandbox only what they name. Two things are given to every tool; the dangerous capabilities are strictly opt-in; everything else is denied.

Granted to every tool
  • stdout / stderr — logging surfaces in harness logs
  • OLIVIA_TOOL_* env — only prefixed vars, prefix stripped
Opt-in, only when declared
  • network raw outbound TCP + DNS, plus WASI HTTP
  • file-system a private per-session /sandbox, read/write
Always denied
  • Any capability not declared
  • Any other filesystem path
  • Inbound sockets, process args, un-prefixed env

Per-session sandbox isolation

A file-system tool sees a single writable directory, /sandbox. On the host each session lives under its own private subdirectory (<sandbox>/<session_id>), mounted into the guest as /sandbox — so one run can never read another's files, and the mount is the only thing that confines writes.

Stateless by construction

Every invocation gets a fresh Store. No memory, no filesystem handles, and no capabilities leak from one tool call to the next.

Get started

Describe an agent. Point services at it. Run.

Run the stack

The dev stack brings up the harness alongside a LiteLLM proxy, a local Ollama, the tools builder, and the backing services tools reach.

shell
# build & run everything (sources .env.develop)
make develop

# pull the model referenced by the LiteLLM config, once
docker compose exec ollama ollama pull gemma4:12b
